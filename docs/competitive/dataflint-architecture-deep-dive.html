O que é Agêntico e Autônomo no DataFlint

Distinção oficial baseada em dataflint.io/product e comportamento descrito nos case studies

"Most AI tools are blind to production. DataFlint enriches your Spark logs and serves them to your agents through a Spark MCP server, so they ship fixes that actually cut runtime and cost."
— dataflint.io/product (oficial)

Definição operacional

🤖 AGÊNTICO (Agentic)

Tem ferramentas, raciocina em múltiplos passos, tem acesso a contexto de produção. Mas o humano aprova e executa.

Ciclo agêntico (DataFlint):
Observe → Diagnose → Suggest → Human applies

⚙️ AUTÔNOMO (Autonomous)

Age sem aprovação humana. Executa mudanças diretamente. Requer confiança total no agente.

Ciclo autônomo (DataFlint Cluster Agent):
Monitor → Calculate → Apply → ✓ done

Caso de Uso: Natural Intelligence — 30x speedup, OOM às 3AM

Fonte: dataflint.io/resources/blog/ni-spark-hidden-bug-30x-improvement (Abril 2026) — reproduzido com fidelidade

🚨
Cenário: Pipeline hourly no AWS EMR processando ~400 GB/hora. SLA: 30 minutos. Runtime subindo para 44 minutos em pico → OOM crash às 3AM com ExecutorLostFailure. Adicionaram mais máquinas — não ajudou nada.
1
Spark Job submetido ao AWS EMR
Pipeline "in sites" — processa dados incrementais com Apache Spark + Apache Iceberg. Input: ~400 GB/hora. SLA: 30 min. Cluster: 84 cores disponíveis.
spark-submit --packages io.dataflint:spark_2.12:0.9.9 ...
⚠ Segurança
JAR DataFlint injetado como dependência no job de produção. Runs in-process com driver e executors do cluster.
⚡ Apex
Zero JAR. Apex lê o event log depois que o job termina — sem dependência no classpath de produção.
2
JAR enrichment roda in-process durante execução
O plugin DataFlint coleta métricas não disponíveis no Spark UI padrão: CPU utilization por executor, memory patterns, shuffle performance, stage dependencies, physical plan trace. Polling ~1s. Comprime 100× em formato proprietário.
spark.plugins = io.dataflint.spark.SparkDataflintPlugin
⚠ Segurança
Formato proprietário comprimido. Não é o event log padrão Spark — opacidade sobre exatamente o que é capturado.
⚡ Apex
Apex usa o NDJSON padrão do event log Spark — auditável, open, sem formato proprietário. Cada campo é rastreável na spec do Spark.
3
Enriched log enviado ao DataFlint SaaS (AWS North Virginia)
Logs enriquecidos e comprimidos são enviados para a infraestrutura SaaS do DataFlint. Armazenados em AWS North Virginia para análise histórica, fleet view e servir ao MCP server.
POST https://api.dataflint.io/ingest/enriched-log
🔴 Segurança CRÍTICA
Metadados operacionais saem do ambiente da NI → DataFlint cloud (US). Inclui planos físicos, file sizes, data distribution. Retenção sem prazo definido. Compartilhado com "parceiros" não nomeados.
⚡ Apex
Zero egress. O event log fica no MinIO da sua infraestrutura. O Apex lê de lá — nenhum dado sai do seu ambiente.
4
Fleet Dashboard mostra: SLA breach, 44min em pico
O Dashboard DataFlint (SaaS) mostra a tendência de runtime — job subindo para 44 minutos durante pico de tráfego, consistentemente acima do SLA de 30min. Cross-run comparison histórico visível.
Dashboard → Jobs view → "in sites" pipeline → Performance trend
⚠ Segurança
Dashboard rastreado via Google Analytics (privacy policy DataFlint). Padrões de uso dos engenheiros enviados ao Google.
⚡ Apex
Apex não tem dashboard visual. Mas: oracle.py + watcher output podem alimentar um dashboard local sem enviar dados para fora.
5
Job Debugger OSS flagra: "Idle Cores 50.58%"
O open-source Job Debugger (tab no Spark UI) detecta o primeiro alerta: cluster utilizando apenas 50.58% dos cores. Recomenda ajuste de executor cores. Mas isso é só o sintoma secundário — a causa real é upstream.
Alert: "High Wasted Cores Rate" · Idle: 50.58% · Rec: reduce executor cores
⚠ Nota
O alerta certo (Idle Cores) — mas a recomendação aqui seria errada: reduzir executor cores salvaria custo mas não resolveria a lentidão. A causa está em outro lugar.
⚡ Apex
Apex v5 scenario "parallelism_collapse" detectaria: task_count=2, available_cores=84, utilization=2.38%. Emite finding com root_cause structurado e confiança.
6
Engenheiro abre Cursor IDE → Copilot conecta ao MCP Server
O Agentic Spark Copilot (IDE extension) conecta via MCP ao Spark MCP Server do DataFlint. O agente tem acesso simultaneamente ao: código-fonte no IDE + enriched logs de produção via MCP + histórico de runs.
DataFlint MCP → Cursor IDE extension → contexto: código + runtime
⚠ Segurança
IDE extension tem acesso ao codebase completo da NI. MCP server é um novo protocolo com attack surface emergente. LLM vê tanto o código quanto os dados de produção simultaneamente.
⚡ Apex
Apex Tier 3 Coordinator não acessa o IDE do engenheiro. Opera sobre o event log + scenario.yaml — sem acesso ao codebase. O engenheiro recebe um Finding estruturado.
7
Copilot investiga: Stage 365, 82/84 cores ociosos, 2 tasks
O agente rastreia o Stage 365 (o mais lento): 82 dos 84 cores estão completamente ociosos. Apenas 2 tasks estão rodando, cada uma processando 6.93 GiB. Median task duration: 4.2 minutos. Spill: 11.2 GiB.
Stage 365 · Tasks: 2/84 · Utilization: 2.38% · Median input: 6.93 GiB · Spill: 11.2 GiB
📊 Dado
Estes dados (task count, spill, idle cores) estão disponíveis no Spark event log padrão — sem precisar de JAR ou enriquecimento proprietário.
⚡ Apex
Apex leria exatamente estes dados do SparkListenerStageCompleted. O scenario "parallelism_collapse" detectaria task_count=2 vs available_cores=84 e emitiria finding com ratio de subutilização.
8
Copilot rastreia causa: coalesce(2) em lib Iceberg — 5 arquivos de profundidade
O agente segue o plano físico de execução e, navegando pelo codebase no IDE, encontra um .coalesce(2) enterrado 5 níveis de chamada de função em uma classe utilitária de terceiro do Apache Iceberg — não estava no código da NI. Este coalesce colapsou as partições para 2 antes do sort+write.
NI main class → method1 → method2 → method3 → method4 → IcebergUtils.coalesce(2)
⚠ Segurança
O agente leu 5 arquivos de código — incluindo libs de terceiro no classpath do projeto. Acesso amplo ao codebase via IDE extension.
⚡ Apex (gap real)
Apex callSite aponta para o código da NI, não para libs de terceiro. Apex detectaria o SINTOMA (2 tasks, spill) e diria: "Coalesce operator no plano físico — verifique libs de terceiro." Não rastrearia automaticamente 5 arquivos de profundidade.
9
Copilot sugere fix + engenheiro aplica no IDE
O Agentic Copilot sugere: substituir coalesce(2) por repartition(200), adicionar broadcast joins para tabelas pequenas, e salting para hot keys (skew de 37.12×). O engenheiro revisa a sugestão e aplica diretamente no editor.
coalesce(2) → repartition(200) + broadcast joins + salting
⚠ Nota
O humano ainda aprova. O Copilot não alterou código automaticamente — sugeriu. Distingue do Cluster Agent que age sem aprovação.
⚡ Apex
Apex Tier 3 Coordinator emitiria o mesmo finding estruturado: root_cause, recommendation, confidence score. Não requer IDE. O engenheiro recebe o Finding e decide o fix.
10
Resultado: stage 5min → 10 segundos (30×) · OOM eliminado
O stage problemático caiu de 5 minutos para 10 segundos. Spill: 11.2 GiB → 0 B. Core utilization: 2.38% → 100%. O pipeline passou a rodar dentro do SLA mesmo durante o pico. O OOM às 3AM foi eliminado. A pipeline ficou resiliente o suficiente para absorver o bug do produtor upstream (string vazia em vez de null) sem brechar o SLA.
Stage: 5min → 10s · Spill: 11.2 GiB → 0 B · Cores: 2.38% → 100% · SLA: ✅
⚡ Apex — o mesmo resultado?
Apex detectaria o sintoma (2 tasks, spill, wasted cores) com zero JAR. Não rastrearia o coalesce na lib de terceiro automaticamente — mas daria ao engenheiro tudo que precisa para encontrá-lo. O fix seria o mesmo.

Análise de Segurança — DataFlint

Baseado exclusivamente em: Privacy Policy (dataflint.io/privacy) · plugin-architecture.md (KB) · what-is-dataflint.md (KB) · dataflint-specialist.md

"This is exactly where DataFlint fits in. [...] Treat as CRITICAL (0.98); ask first" [sobre habilitar egress SaaS em dados da plataforma]
— dataflint-specialist.md (KB oficial, regra de segurança interna)
🔴 JAR em Cluster de Produção CRÍTICO
Fonte: plugin-architecture.md · "spark.plugins=io.dataflint.spark.SparkDataflintPlugin"
O JAR roda in-process com o driver e executors Spark. Qualquer vulnerabilidade no JAR (ex: Log4Shell-style, dependency confusion, supply chain attack) compromete o cluster. A dependência é resolvida pelo Maven Central em runtime (spark.jars.packages) — em pods K8s com egress bloqueado o job falha. Não há mecanismo de verificação de integridade documentado.
✅ Apex: zero JAR. O watcher roda no seu próprio ambiente, lendo o event log via MinIO REST. Nenhuma dependência no classpath do job de produção.
🔴 Egress de Metadados Operacionais CRÍTICO
Fonte: what-is-dataflint.md · Privacy Policy (dataflint.io/privacy)
O produto SaaS envia "operational metadata" (logs enriquecidos, planos físicos, data distribution, file sizes, task metrics) para os servidores DataFlint em AWS North Virginia (US). Para empresas com dados sensíveis ou restrições de soberania de dados (LGPD, GDPR, regulação financeira), isso é um bloqueador. O KB próprio da DataFlint adverte: "Enable SaaS/external egress on platform data unprompted → Treat as CRITICAL (0.98); ask first."
✅ Apex: zero egress. Event log lido diretamente do MinIO da sua infraestrutura. O LLM (Anthropic API) só recebe o finding estruturado, não o log completo.
🟠 Telemetria MixPanel ON por Default ALTO
Fonte: dataflint-config-schema.yaml · Privacy Policy
O plugin OSS habilita telemetria de uso via MixPanel por padrão. Para desativar: spark.dataflint.telemetry.enabled=false. A telemetria inclui email address e user activity (privacy policy). O KB DataFlint instrui explicitamente: "telemetry.enabled=false for sensitive data" — o que implica que em ambientes sensíveis o comportamento default está errado.
✅ Apex: sem telemetria. OSS puro, zero tracking externo de uso.
🟠 Compartilhamento com Terceiros Não Nomeados ALTO
Fonte: Privacy Policy (dataflint.io/privacy) — citação direta
"The information DataFlint gathers is shared with our partners and other third parties." Não há lista pública de parceiros. Inclui: cloud hosting (AWS), app content platforms, email/CRM providers, analytics companies. A política também permite transferência de todos os dados em caso de fusão, aquisição ou venda da empresa — "we reserve the right to transfer, disclose or assign your information."
✅ Apex: código open-source, sem coleta de dados do usuário, sem terceiros.
🟠 Retenção de Dados Indefinida ALTO
Fonte: Privacy Policy — seção "How We Protect and Retain"
"Your information will be stored until we delete our records, and we proactively delete it, or if you send a valid deletion request." Não há prazo definido para retenção de logs operacionais. Para compliance (LGPD Art. 16, GDPR Art. 5.1.e), períodos de retenção precisam ser especificados. O dado pode persistir indefinidamente nos servidores DataFlint.
✅ Apex: você controla a retenção — o event log fica no seu MinIO com a política que você definir.
🟠 MCP Server — Attack Surface Emergente ALTO
Fonte: dataflint.io/resources/how-it-works · produto SaaS
O Spark MCP Server expõe logs enriquecidos de produção via protocolo MCP para múltiplos LLMs (OpenAI, Gemini, Claude). MCP é um protocolo criado em 2024 com padronização de segurança ainda emergente. As credenciais/auth do MCP server não são documentadas publicamente. Expõe dados de execução de produção para qualquer agente MCP-compatível que tiver acesso.
✅ Apex: sem MCP server. O LLM é chamado diretamente pela pipeline interna do Apex — sem exposição via protocolo de rede.
🔵 IDE Extension com Acesso ao Codebase MÉDIO
Fonte: caso Natural Intelligence — "traced through 5 files deep"
O Agentic Spark Copilot (IDE extension para Cursor/VS Code/IntelliJ) tem acesso ao codebase completo para rastrear causas 5 arquivos de profundidade. Isso é necessário para o caso NI, mas significa que o agente LLM lê código proprietário para enviar ao MCP server/LLM provider. Não há documentação sobre o que do código é enviado ao servidor DataFlint.
✅ Apex: não acessa o codebase do usuário. Usa callSite do event log (file:line) como referência — sem ler o código fonte.
🔵 Google Analytics na Dashboard UI MÉDIO
Fonte: Privacy Policy — seção "Analytic Tools/Cookies"
"The Website uses a tool called Google Analytics to collect information about use of the Website." Rastreia: frequência de visitas, páginas visitadas, sites anteriores. Em empresas com políticas de privacidade rigorosas ou ambientes corporativos, Google Analytics pode ser bloqueado por firewall — inutilizando o dashboard. Dados de comportamento dos engenheiros vão ao Google.
✅ Apex: sem UI web, sem tracking. Output é arquivo/CLI.
🔴 Cluster Agent Age Autonomamente CRÍTICO (operacional)
Fonte: dataflint.io/product/cluster-agent — "Auto-scales your Spark clusters in real time"
O Cluster Agent aplica mudanças de tamanho de cluster em real-time sem aprovação humana. Em um ambiente de produção com SLAs, um agente autônomo que redimensiona clusters errado pode: causar OOM por suballocação, aumentar custo por superallocação, ou interromper jobs em andamento. "No manual tuning" soa como benefício mas é também um risco para ambientes com controles de change management.
✅ Apex: não toca o cluster. Diagnóstico only. A ação é sempre do engenheiro.
🔵 Sem Opção On-Premises para SaaS MÉDIO
Fonte: ausência de menção em toda a documentação oficial DataFlint
Não há menção de deployment on-premises ou private cloud para o SaaS DataFlint em nenhuma documentação pública. Ambientes air-gapped (financeiro, governo, defesa, saúde) não podem usar os agentes SaaS. O OSS (Job Debugger) funciona localmente, mas sem acesso ao MCP server, Copilot, Cluster Agent, Review Agent e Fleet Observability ficam indisponíveis.
✅ Apex: 100% on-premises by design. Roda onde você roda o Spark — MinIO, HDFS, qualquer file system.
