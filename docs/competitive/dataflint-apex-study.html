O que é cada produto

DataFlint OSS

Drop-in Spark UI Replacement

"Spark Performance Made Simple" — plugin que adiciona uma aba ao Spark UI existente com alertas nomeados de performance. Diagnóstico apenas. Nunca altera o plano de execução.

Intrusividade: JAR + spark.plugins obrigatório
Quando age: Live (driver:4040) + History Server
Output: 14 alertas nomeados na UI
Quem age: Humano lê, humano decide
SaaS paralelo: "Production-Aware AI Agents" (pago)
Apex v4

Agentic Diagnostic Engine

Sistema de diagnóstico em 4 tiers que lê event logs do Spark via MinIO REST. Detecta anti-patterns, classifica com LLM, orquestra diagnóstico e julga com alta confiança. Zero injeção.

Intrusividade: Zero JAR · Zero listener · Zero SparkSession
Quando age: Pós-execução (event log MinIO)
Output: Finding nomeado + root_cause + recomendações
Quem age: Apex raciocina e entrega diagnóstico
Validação: oracle.py valida sintético vs real

Arquitetura DataFlint

Premissa central: DataFlint usa a interface SparkPlugin (nativa desde Spark 3.0) para se registrar in-process no driver. Lê o mesmo event/metric stream da Spark UI — não altera planos, não injeta código no executors.
Hook de Ativação

Dois configs — sem mais nada:

spark.jars.packages io.dataflint:spark_2.12:0.9.9 spark.plugins io.dataflint.spark.SparkDataflintPlugin
Pipeline Interno
SparkContext start └─ instantiate SparkDataflintPlugin └─ attach to event/metric stream └─ serve via Spark UI endpoint └─ evaluate metrics → named alerts
Dois Modos
ModoFeedURL
Live DriverListener bus ativo:4040/DataFlint
History ServerEvent logs replay:18080/DataFlint
Segurança / Remoção

Remove limpamente: deletar os dois configs. Zero migração, zero estado residual.

Telemetria: MixPanel anônimo (Spark ver + App ID apenas). Desabilitar: spark.dataflint.telemetry.enabled=false

Arquitetura Apex (comparada)

Premissa Absoluta

Zero JAR · Zero listener · Zero modificação de SparkSession
Leitura passiva do event log via MinIO REST

python watchers/skew_watcher.py \ scenarios/skew_on_join_30x.yaml \ s3a://spark-logs/events/app-id
4-Tier Pipeline
Tier 1 Watcher → determinístico Tier 2 Classifier → LLM nomeia Tier 3 Coordinator → Sonnet orquestra Tier 4 Judge → Opus (conf < 0.6)
Contrato scenario.yaml

Cada anti-pattern definido em YAML. Desacopla code_generator de plan_generator. Oracle valida sintético vs real.

Cadeia de Custódia

scenario_hash (sha256:16) embutido no log sintético e no manifesto do job. Watcher rejeita log stale automaticamente.

Onde o Apex compete com o DataFlint pago

Insight crítico: O DataFlint OSS é o detector gratuito. O produto pago deles (dataflint.io) é um "Production-Aware AI Agents for Spark" com MCP + 4 agentes. O Apex compete com o tier pago, não com o OSS. O OSS é o benchmark; o SaaS é o concorrente.
DataFlint SaaS (concorrente real)

4 Agentes + MCP Server

Agentic Spark Copilot (IDE) · Cluster Agent (right-sizing) · Review Agent (PR regressions) · Fleet Observability. SOC 2 Type II. Envia operational metadata externamente.

Apex — Diferenciação

Loop Fechado + Validação

Não-intrusivo (zero JAR) · Diagnóstico automático sem UI · Validação via oráculo · scenario.yaml extensível · Pipeline agentic 4-tier com confiança graduada.

Decisão Estratégica — Baseada no Sync (09 Jun 2026)

O OwsHQ colocou a pergunta no Discord: "Conseguimos ter acesso ao código sem ser intrusivo?" A análise do DataFlint como benchmark responde essa pergunta com evidência empírica.

Árvore de decisão: biblioteca vs beacon

❓

O objetivo do Apex é recomendar melhoria de código?

O OwsHQ quer "Fix it / Optimize" como o Databricks faz. Isso requer o código-fonte.

📚

Sim → Biblioteca é necessária

O DataFlint confirma: mesmo com JAR intrusivo, eles não acessam código-fonte. Para recomendação de código é preciso ou (a) biblioteca que captura no ponto de execução, ou (b) beacon + Git API. Pivot confirmado pelo benchmark.

🎯

Não → Beacon é suficiente para Tiers 1-2

Se o objetivo é diagnóstico não-intrusivo de anti-patterns (skew, spill, broadcast), o Apex já faz mais que o DataFlint OSS com zero JAR. Beacon + callSite cobre 80% dos casos.

🏛

Recomendação: ADR para definir o produto

Essa é uma decisão de produto, não técnica. As duas opções são viáveis — mas levam a produtos diferentes. Deve virar ADR-005 com posicionamento claro: "Apex = diagnóstico não-intrusivo" OU "Apex = copilot com code access". Não os dois ao mesmo tempo no v0.
