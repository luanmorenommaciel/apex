## Observed results

- Two distinct real Spark jobs each processed 10 million joined rows with identical aggregate output and 20 observed stages. Both Engine/Serve gates passed.
- Seven selected argument sets across four tools produced identical parsed JSON over HTTP and real stdio MCP sessions with API and direct-ClickHouse backends: analysis for each job; forward, reverse and missing-baseline comparisons; recall; and unassessed verification. This is not all-eight-tool coverage, MCP-over-HTTP transport testing or desktop-client onboarding.
- Real Chrome checked populated Compare and Memory. Selected cards and stage rows matched independent calculations from resource data. Shuffle totals were identical; spill changed from 174,995,630 to 152,120,469 bytes and GC from 2,911 to 3,605 ms. No noise floor was measured, and no tuning benefit is claimed. Run wall clock remained unknown.
- Actual Memory indexing produced 16 stored outcomes. The API's eight listed shapes expose 14 of them; two belong to a one-node shape excluded by the documented plan index filter. All 16 task-time aggregates were checked against captured stages.
- Verify was checked first without a row, then with one explicitly synthetic verification row. The overlay rendered with human approval required, applied=false, mechanism not stored, runtime unresolved and zero replays. This proves projection/rendering, not prediction, replay, safety evaluation or a certified fix. Separate browser-injected 503 controls tested failure-versus-empty presentation.
- Actual 401, 502 and 504 responses, cache before/after expiry and same-session recovery with a fresh 200 were observed. The first API suspension instead produced a browser network failure at 32.34 seconds and nginx 499. That result is retained. Two bounded follow-ups received real 504 near 60 seconds from both Chrome and an in-container client; the final repeat explicitly recorded fresh 200 recovery.

Four selected captured settings matched between jobs. Executor memory was absent in both job_conf API captures and was not imputed.

## Interpretation and discussion points

The Console classified the pair as `unchanged`, while the API and both MCP backends returned `regressed`. Numeric consistency is not common verdict semantics: the Console's comparison status focuses on shuffle changes; the backend also considers plan and finding changes. This offers a concrete P7.2 discussion case without selecting option A or B.

Exactly stage 16 had different fingerprints. Captured normalized plan strings reproduce both hashes; their sole changed line reorders top-level arguments of a commutative-expression representation. The printed argument multisets match. This explains the string/hash difference, but does not prove semantic equivalence, identify UDF implementation/state, or establish a Spark/APEX defect. The backend also reported finding changes, so its status cannot be attributed solely to the fingerprint. #185 was not tested and is not claimed as a fix.

The captures also show wording that attributes a result to growing input or AQE without those mechanisms being demonstrated by this experiment. These are opportunities to clarify evidence boundaries with the authors, not a claim that the product executed a tuning intervention.
