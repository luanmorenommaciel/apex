Diagnóstico v1 · o que estava quebrado (rodamos e provamos)

Os três defeitos
que quebravam a tese.

Defeito 1 · linha do anti-pattern era ficção
Contrato: linha 58. Código gerado: linha 29. Arquivo tem 34 linhas.
A tese central do Luan é correlacionar a coordenada do log (job.py:linha) com a linha no repositório. O contrato mentia sobre a linha — a correlação já nascia quebrada.
Defeito 2 · campos do log sintético não existem no Spark real
taskMetrics.shuffleReadMetrics.recordsRead não existe no Spark.
O campo real é Task Metrics → Shuffle Read Metrics → Total Records Read (JsonProtocol, capitalizado). Um Watcher feito contra o v1 não leria log de produção. O oráculo nunca conseguiria comparar.
Defeito 3 · sem distribuição, não há skew
1 task no log sintético. Skew é a cauda — não a média.
O Aguimar explicitou no deck: "não a média, mas a cauda." Com uma task só, não há com quem comparar. Nenhum detector de skew poderia funcionar contra esse log.

O que a v2
entrega rodando.

Correção 1 · Guard de linha (nunca mais divergência silenciosa)
O gerador calcula a linha real e FALHA se divergir do contrato.
Se alguém mexer no template e a linha mudar, o code_generator aborta com mensagem clara. Contrato e código são mantidos em sincronia por CI, não por combinado verbal.
Correção 2 · Schema fiel ao Spark (JsonProtocol real)
Log sintético usa os nomes de campo REAIS do Spark 4.1.2.
Baseado no mapeamento do Gabriel (119/119 linhas validadas no plat-v0). Um Watcher escrito contra o sintético lê log de produção também — sem adaptação.
Correção 3 + Skew Watcher · distribuição derivada e loop fechado
8 tasks com cauda real: 27.9× de skew ratio, derivado dos dados.
O skew_watcher detecta pela cauda, emite Finding com confiança da evidência, e valida contra o acceptance. O gate de CI sai verde. Isso é o que o Luan chamou de "simples demonstração desse pedaço" — o escopo funcional.

Rodamos o job gerado no Spark 4.1.2 real com event log. Três comportamentos do AQE se manifestaram — o Aguimar já havia alertado no deck ("o plano inicial não é o executado"). Agora temos a prova empírica.

Isso confirma empiricamente o alerta do Aguimar: o plano executado não é o plano inicial. O Watcher que ler só o physicalPlanDescription do evento de início estará lendo o plano antes do AQE agir.

Implicação direta · como os Watchers devem ser escritos

O que o AQE
muda no Watcher.

Ler o plano certo
Não: physicalPlanDescription do início.
Sim: physicalPlanDescription do último SparkListenerSQLAdaptiveExecutionUpdate.
O plano inicial é a intenção; o final é a verdade.
Detectar pela distribuição
Não: "task X leu N registros".
Sim: "task X leu K vezes a mediana das outras tasks do mesmo stage".
Skew só existe em relação às outras. Uma task isolada não tem com quem comparar.
Filtrar pelo stage certo
Não: todas as tasks do job.
Sim: tasks do stage com o maior shuffle read.
Tasks de scan têm Total Records Read = 0 e distorcem a mediana se incluídas.
O fixture foi endurecido com base nesses achados
O scenarios/skew_on_join_30x.yaml agora inclui configs que garantem que o skew se manifesta: coalescePartitions.enabled=false, ambos os thresholds de broadcast em -1, e um hint("shuffle_merge") no join. Cada config veio de uma falha real no run — não são parâmetros arbitrários.
