Contexto

Reunião de alinhamento de 30/06 — Escopo V0.1

📌 O que está em discussão

  • Durante a reunião de 30/06, identificamos duas frentes de desenvolvimento paralelas para o Apex
  • A branch cowork evoluiu com agentes CrewAI, testes e estrutura V1
  • A branch kimi avançou com Go, documentação técnica e ADRs
  • Ambas possuem valor, mas correm o risco de divergir permanentemente
  • Esta apresentação propõe uma arquitetura híbrida que unifique o melhor das duas vertentes

Branch cowork

Agentes colaborativos e orquestração com CrewAI

🚀 O que entrega hoje

  • CrewAI: Orquestração multi-agente com papéis definidos (pesquisador, escritor, revisor)
  • V1 Architecture: Estrutura modular de agentes com memória e ferramentas
  • Testes: Suite de testes unitários e de integração para os agentes
  • Flows: Pipelines de execução sequencial e hierárquica de tarefas
  • Callbacks: Hooks para monitoramento e telemetria da execução

Branch kimi

Core em Go, documentação estratégica e decisões arquiteturais

⚙️ O que entrega hoje

  • Go Core: Engine de execução em Go com alta performance e baixa latência
  • Documentação: Docs técnicos completos (README, arquitetura, guias)
  • ADRs: Architecture Decision Records registrando porquê de cada escolha
  • Desacoplamento: Separação clara entre geração de conteúdo e orquestração
  • API REST: Interface limpa para integração com outros sistemas

Gaps Identificados

O que falta em cada vertente para atingir a V1.0 unificada

🔵 Orquestração

A branch kimi ainda não tem orquestração multi-agente. Precisamos portar o modelo de tasks do CrewAI ou implementar equivalente nativo em Go.

🟠 Performance

A branch cowork depende do Python, o que impõe limites de latência. O core em Go da kimi pode ser o "motor", mas precisa de bindings.

🟡 Testes

A kimi carece de testes robustos. A cowork tem testes, mas precisam ser adaptados para uma arquitetura híbrida.

🟢 Documentação

A cowork tem docs esparsos. Precisamos unificar a documentação em um único portal com ADRs que cubram todo o sistema.

🔴 API Unificada

Não existe uma API única que exponha tanto a orquestração CrewAI quanto o core Go. Isso é crítico para integração.

🟣 Estado / Memória

A persistência de estado entre execuções é tratada de forma diferente em cada branch. Precisamos de uma camada comum.

Decisões Pendentes do Commander

O que precisamos que o Luan defina para seguir

1
Prioridade de performance vs. velocidade: Mantemos CrewAI como orquestrador principal (mais rápido de implementar) ou investimos no orquestrador nativo Go já na V0.2?
2
Stack de testes: Unificamos em Go (testes de integração) ou mantemos testes Python para a camada de agentes?
3
Timeline: Qual é a data-alvo para V0.1 estar em produção? Isso define se fazemos merge rápido ou refinamos antes.
4
Escopo de agentes: Quantos agentes-piloto na V0.1? Apenas os 3 do CrewAI ou incluímos novos papéis já na unificação?
