# LLM Solution Validation Framework

Date: 2026-07-09
Branch: `gustocezar/feature/codex-desacoplamento-geradores`
Prepared by: Codex

## Purpose

This framework defines how Apex will compare, validate, and refine solutions generated by different LLMs or agentic workers.

The goal is not to pick a favorite LLM. The goal is to build the best Apex solution possible from all candidate solutions, while following Commander Luan's premises and protecting the branch currently under remote review.

## Operating Rule

Every LLM-generated solution is a candidate. No candidate is accepted by narrative alone.

Each candidate must be evaluated through:

- source code evidence;
- runnable tests or reproducible commands;
- real or fixture Spark event logs;
- alignment with Luan's architecture;
- comparison against DataFlint capabilities;
- explicit risk and gap analysis.

Codex is the local synthesis and validation branch. Codex may absorb ideas from other branches, but only after converting them into tested, reviewable, local changes.

## Commander Luan Premises

Every candidate solution must map to these premises:

| Premise | Required Evidence |
| --- | --- |
| Reproducible Spark environment | Docker, local setup, or documented existing platform that can run jobs consistently |
| Event capture | SparkListener, event log parser, or equivalent stream that captures Spark execution data |
| ClickStack/ClickHouse telemetry | Metrics persisted/queryable by `job_id` or `app_id` |
| Diagnosis by `job_id` | A deterministic command/tool can answer "what happened in this job?" |
| Agentic reasoning | LLM/agent adds reasoning only after evidence is available |
| Autonomy with guardrails | Fixes are previewed or require explicit approval before modifying files |
| MCP/IDE delivery | Findings can be exposed to an engineer in the IDE |
| Closed loop | Detect -> validate -> recommend -> preview/apply -> verify |
| Local/on-prem viability | Basic diagnosis must work without sending data to an external SaaS |
| Branch safety | No remote branch under review is modified without explicit approval |

## Candidate Solution Intake

Each LLM or worker must submit a solution in this format:

```markdown
# Candidate Solution: <name>

## Summary
One paragraph explaining the solution.

## Architecture
Diagram or clear data flow.

## Implemented
Concrete files, modules, tests, commands.

## Proposed Only
Ideas that are not implemented yet.

## Validation
Commands that prove the solution works.

## DataFlint Comparison
Where it matches, beats, or falls behind DataFlint.

## Risks
Security, correctness, cost, LLM dependency, merge risk.

## Next Step
One concrete implementation step.
```

Any solution that does not separate implemented work from proposed work is considered incomplete.

## Evidence Levels

| Level | Name | Meaning | Example |
| --- | --- | --- | --- |
| E0 | Claim | Stated in a doc or chat only | "This detects skew" with no code or test |
| E1 | Code exists | A module implements the feature | Detector function exists |
| E2 | Unit tested | Tests cover the feature with fixtures/fakes | `pytest` test for detector thresholds |
| E3 | Local integration tested | End-to-end local command works | `debug_job(job_id)` over NDJSON or ClickHouse |
| E4 | Real evidence tested | Tested with real Spark event log or local Spark run | `real_log.ndjson` produces expected finding |
| E5 | Operationally proven | CI, repeatability, docs, and failure handling exist | Scheduled oracle plus manual replay |

Decision rule:

```text
E0-E1: idea only
E2: candidate component
E3-E4: usable in Codex integration
E5: candidate for V1 baseline
```

## Scoring Criteria

Each candidate is scored from 0 to 5 per dimension.

| Dimension | Weight | What 5 Means |
| --- | ---: | --- |
| Luan architecture fit | 5 | Covers Spark env, telemetry, ClickHouse, diagnosis, MCP, guarded fix |
| Evidence strength | 5 | Has tests and real-log/local-run validation |
| Detector coverage | 4 | Covers multiple Spark anti-patterns, not only skew |
| False-positive control | 5 | Has validator, thresholds, and negative baselines |
| Closed-loop IDE UX | 4 | Engineer can diagnose and preview/apply fix from IDE |
| Local/on-prem safety | 4 | Works without external SaaS/LLM for basic diagnosis |
| Merge safety | 4 | Can be imported without destructive repo rewrite |
| DataFlint competitiveness | 3 | Matches or beats DataFlint in one or more meaningful dimensions |
| Governance | 3 | Has ADRs, traceability, issues, and clear ownership |

Weighted score:

```text
score = sum(points * weight)
```

Scores are guidance, not authority. A low-scoring solution may still provide one excellent component.

Gate 7 is complete locally against a real ClickHouse HTTP endpoint:

Gate 10 is complete locally for recommend/preview:

- MCP exposes both tools as read-only;
- `apply_fix` remains absent.

Gate 11 is complete locally for guarded apply/verify:

- `preview_recommendation` returns `before_sha256`, `after_sha256`, `diff_sha256`, and an approval token;
- `apply_recommendation` writes only when `apply_root` is configured and the approval token still matches the current preview;
- `verify_recommendation_apply` confirms the final file hash;
- MCP marks `apply_recommendation` as non-read-only guarded mutation;
- `apply_fix` remains absent and rejected.

Gate 12 is complete locally for before/after telemetry comparison:

- `compare_job_telemetry(before_job_id, after_job_id)` compares telemetry already collected in NDJSON or ClickHouse stores;
- comparison covers finding count, resolved/new finding kinds, skew ratio, spill bytes, GC ratio, OOM failures, and AQE updates;
- result status is `improved`, `regressed`, `unchanged`, `mixed`, or `not_comparable`;
- MCP exposes the tool as read-only;
- real ClickHouse integration validates before/after comparison when a local service is configured.

- custom detector authoring;
- issue/ADR traceability;
- preview-first fix application;
- deterministic no-LLM diagnosis path.

## Refinement Loop

Use this loop for every imported component:

1. Identify the source component.
2. Classify its evidence level.
3. Write or port a focused test into Codex.
4. Import the minimum code needed.
5. Run focused test.
6. Run full Codex test suite.
7. Update comparison matrix.
8. Only then consider the component accepted.
