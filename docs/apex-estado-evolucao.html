scenario.yaml — O contrato que evita alucinação

O que Luan pediu: contratos para a LLM não alucinar

O scenario.yaml IS o contrato. Ele declara o que o problema é, como validar, e quais critérios de aceitação. A LLM lê esse contrato e não pode inventar fora dele.

scenario_id: skew_on_join_30x
version: 3
status: prototype

acceptance:               ← critérios que o Watcher DEVE satisfazer
  min_ratio: 10.0         ← skew ratio mínimo detectável
  hot_key_present: true   ← hot key deve estar no finding

code_generator:           ← gera o job PySpark com o anti-pattern
  anti_pattern: skew_join
  hot_key_factor: 30

plan_generator:           ← gera o event log sintético calibrado
  target_ratio: 30.0
  total_tasks: 8
  hot_partition_tasks: 1

oracle:                   ← valida sintético vs real
  tolerance: 0.15         ← 15% de tolerância
⚠ O v1-skeleton NÃO tem scenario.yaml. Isso significa que o SparkListener vai capturar dados reais, mas sem contrato declarativo — a LLM pode alucinar porque não há critério de aceitação definido. Para evitar isso, o v1-skeleton precisa de: (1) um schema de validação do finding, e (2) um contrato mínimo de o que esperar de cada anti-pattern.

Caso de Uso — skew_on_join_30x (fim a fim)

O único anti-pattern validado hoje. Use como template para os próximos 12.

🚨 O Problema

Um job PySpark faz JOIN entre uma tabela grande e uma tabela de lookup. A chave de join tem uma hot key — um valor que aparece muito mais que os outros (30x). O Spark distribui igualmente os dados por partição, mas a hot key acaba em uma única task que processa 30x mais dados que as outras. O job leva horas. Adicionar mais recursos não resolve.

✅ O que o Apex detecta

Sem instalar JAR, sem modificar o cluster: o Apex lê o event log padrão Spark no MinIO, calcula o ratio máx_task/mediana, identifica a hot key responsável, e emite um finding estruturado com root_cause, hot_key, ratio, e recomendação concreta.

Passo a passo completo

#AçãoQuemResultado
1scenarios/skew_on_join_30x.yaml define o contrato: ratio mínimo 10x, hot_key_present: true, 8 tasksEngineerContrato declarativo com acceptance criteria
2python generators/code_generator.py scenario.yaml job.pyClaudejob.py com hot key 30x e sentinela de linha
3python generators/plan_generator.py scenario.yaml log.ndjsonClaudeEvent log sintético com ratio 27.9x
4python watchers/skew_watcher.py scenario.yaml log.ndjsonApexFinding: skew detectado, ratio=27.9x, hot_key=val_0

O que o v1-skeleton adiciona (quando validado)

No v1-skeleton, o mesmo finding seria entregue via MCP ao Claude Code / Cursor enquanto o job ainda está rodando (ou logo após terminar). O engineer pergunta: "O que está errado com job ID X?" e o MCP consulta o ClickHouse, obtém as métricas, chama a Claude API, e retorna: "Stage 2 tem skew 27.9x na chave join_key. Hot key: val_0. Recomendação: salting + repartition(50)."

⚠ Esse fluxo ainda não está testado — é o objetivo do v1-skeleton. O Mundo A (atual) já entrega o mesmo finding, só que via CLI em vez de MCP.
