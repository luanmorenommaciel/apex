1 · Visão geral e premissa inegociável

O Apex é um sistema de diagnóstico e recomendação agêntica de performance para workloads Spark. A meta é detectar anti-patterns (data skew, memory spill, broadcast mal dimensionado, etc.) e prescrever correções antes de falhas, em vez de reagir depois.

A tese de mercado: todos os concorrentes (Sparklens, DataFlint, Unravel) param na observabilidade do cluster. Nenhum faz a ponte entre o sinal do log e o código no repositório. E os que chegam perto (Unravel Arvix AI, lançado jun/2026) são comerciais, intrusivos e proprietários.

Premissa inegociável — não-intrusivo
Zero JAR injetado no cluster. Zero modificação da SparkSession. Zero listener de terceiros. Compatível com serverless (onde listeners extras são proibidos). A coleta usa apenas o event log nativo do Spark, lido fora do processo a partir do object storage.

3 · Arquitetura do sistema

O Apex tem quatro tiers de agentes e dois lanes de coleta:

Tier 1 — Watchers (deterministicos)
Pod A1: Shuffle/Skew (Guilherme, Antony)
Pod A2: Memory/Cost (Aguimar, Augusto)
Tier 2 — Classifier (LLM especializado)
Pod A3: Code/AST — lê o repositório, não a telemetria. Depende de acesso ao GitHub.
Tier 3 — Coordinator (Sonnet)
Pod A4: orquestra os Watchers, consolida Findings, emite recomendação com root cause.
Tier 4 — Judge (Opus, confiança < 0.6)
Pod A4: adversarial, escalado pelo Coordinator quando confiança é baixa.

Lane 1 (Dia 1): SparkListener in-process (mais intrusivo; ADR-001). Lane 2 (Sprint 2): event-log tail / SHS REST — leitura out-of-process do storage. O que está implementado e provado aqui é a Lane 2 — a mais não-intrusiva.

5 · O Contrato — scenario.yaml

O scenarios/skew_on_join_30x.yaml é a fonte única da verdade. Ambos os geradores leem o mesmo arquivo independentemente — nenhum chama o outro. É esse desacoplamento que responde à lição de casa do Commander.

scenario_id: skew_on_join_30x
version: 2

anti_pattern:
  class: data_skew_on_join_key   # que bug estamos simulando
  severity: high

code_generator:                   # instrucoes para o job.py
  anti_pattern_line: 21           # linha declarada (v2: fragil — vira output na v3)
  data:
    orders:    { rows: 200000, hot_key: 7, hot_share: 0.80 }
    customers: { rows: 100, distinct_keys: 100 }
  spark_config:
    spark.sql.adaptive.enabled: "false"        # desabilita AQE para fixture deterministico
    spark.sql.shuffle.partitions: "8"

plan_generator:                   # instrucoes para o log sintetico
  expected_signals:
    join_operator: SortMergeJoin
    hot_stage: 4
    skew_ratio_min: 10
    hot_partition: { single_task_shuffle_read_records: 200100 }

oracle:
  tolerance: { skew_ratio: 0.30, records: 0.25 }  # tolerancia ajustada no run real

acceptance:                        # o que o Watcher DEVE detectar (gate de CI)
  root_cause_includes: ["data skew", "customer_id", "SortMergeJoin"]
  min_recommendations: 1

6 · Gerador de código

O generators/code_generator.py lê o contrato e produz um job PySpark com o anti-pattern na linha declarada. Na v2, inclui um guard de linha: o gerador calcula a linha real do join e falha se divergir do contrato — contrato e código não divergem em silêncio.

Fragilidade v2 (será corrigida na v3)
A linha é um input no scenario — qualquer mudança de config desloca o join e exige sed manual para corrigir. Na v3, a linha vira output derivado via sentinela # APEX::ANTIPATTERN gravado num manifesto.

Saída além do job.py: o job usa hint("shuffle_merge") para garantir que o SortMergeJoin ocorra mesmo quando o AQE tentaria broadcast do lado pequeno.

7 · Gerador de plano (sintético)

O generators/plan_generator.py produz um event log em milissegundos, sem executar Spark. O schema usa os nomes de campo reais do Spark JsonProtocol — Task Metrics → Shuffle Read Metrics → Total Records Read — então um Watcher escrito contra o sintético também lê log de produção.

A distribuição de tasks é derivada dos dados do scenario: uma task quente com o volume declarado em single_task_shuffle_read_records; as demais dividem o restante uniformemente. Isso é o que torna o "30x" do nome do cenário um sinal medível, não um número inventado.

8 · O Watcher de Skew

O watchers/skew_watcher.py lê um event log (real ou sintético), detecta o anti-pattern e emite um Finding no formato do watcher.contract. O Finding é validado contra o bloco acceptance do scenario — isso é o gate que o CI checa.

Lógica de detecção

Toma todos os TaskEnd do log, computa max(records) / median(cold_records). Detecção = SortMergeJoin no plano E ratio ≥ skew_ratio_min do contrato.

Band-aid v2 (corrigido na v3)
O Watcher v2 mistura tasks de scan (lêem 0 shuffle) com as de reduce, causando divisão por zero quando as tasks frias mostram 0 records. Solução: cold = [...] or [1]. CAUSA RAIZ: precisa isolar o stage de reduce do join. Correto na v3 via hottest_reduce_stage().

Formato do Finding (saída)

{
  "watcher": "shuffle_skew",
  "severity": "high",
  "confidence": 0.99,
  "evidence": [
    "join operator: SortMergeJoin",
    "task mais pesada (id 4) leu 200100 registros",
    "mediana das demais: 1 -> skew ratio 200100.0x"
  ],
  "root_cause": "data skew na chave de join customer_id (SortMergeJoin): ...",
  "recommendations": [
    "habilitar spark.sql.adaptive.skewJoin.enabled",
    "broadcast o lado customers (dimensao pequena)",
    "salgar a chave customer_id"
  ]
}

9 · O Oráculo de fidelidade

O oracle/compare.py compara o log sintético com o log real, verificando se os sinais detectáveis são fiéis dentro da tolerância do scenario. Garante que o fixture não se descole da realidade do Spark ao longo do tempo.

Sinal comparadoTolerânciaRacional
join_operatorexatoHard — se o plano mudou (ex: AQE fez broadcast), o fixture está errado
hot_records25%Volume da task quente; tolerância ajustada pelo run real (sintético: 160k, real: 200k)
skew_ratiodesabilitadoBand-aid v2: o real colapsou em 1 task (200100x) vs. sintético spread (27.9x); incomparáveis neste ambiente 1-core
Band-aid v2
A comparação de ratio foi desabilitada com if False: porque o real (colapso 1-core) e o sintético (spread 8 tasks) medem distribuições diferentes. Na v3: o oráculo detecta o colapso e emite um aviso honesto em vez de desabilitar a checagem.

10 · Gate de CI

O .github/workflows/scenario-gate.yml roda a cada Pull Request: gera o fixture de cada scenario, roda o Watcher contra o log sintético, e exige gate verde antes do merge.

on: pull_request
jobs:
  gate:
    steps:
      - run: pip install pyyaml
      - python generators/code_generator.py "$s" job.py   # guard de linha
      - python generators/plan_generator.py "$s" log.ndjson # log fiel
      - python watchers/skew_watcher.py "$s" log.ndjson    # detecta + acceptance

11 · Run real no plat-v0 e achados do AQE

Em 05 jun 2026, o job foi submetido ao cluster real via spark-submit --master spark://spv0-spark-master:7077. App ID: app-20260606030054-0000. O Watcher rodou contra o log real baixado do MinIO e emitiu GATE VERDE — a primeira prova com Spark de produção.

3 achados do AQE (mudaram o design)

#AchadoImplicação para o Watcher
1AQE faz coalesce e apaga o skew — juntou as 8 partições em 1 no ambiente 1-coreConfig coalescePartitions=false adicionada ao fixture. Watcher precisa tratar 1 task explicitamente.
2AQE faz broadcast em tempo de execução — converteu SMJ para BroadcastHashJoin apesar do threshold -1 estáticoConfig adaptive.autoBroadcastJoinThreshold=-1 + hint("shuffle_merge") adicionados.
3Plano inicial ≠ plano executado — o physicalPlanDescription no início trazia SMJ, mas o AdaptiveExecutionUpdate mudouO Watcher deve ler o plano final do último SparkListenerSQLAdaptiveExecutionUpdate, não o inicial. Corrigido na v3.
