Resposta curta: sim — pondo um contrato entre eles. Os dois passam a ler o mesmo scenario.yaml, e nenhum depende do outro. Um oráculo periódico mantém a fidelidade. Esta apresentação defende esse desenho e abre os trade-offs pro time decidir se faz sentido.

O que está em jogo
Sem desacoplar, gerar cada caso de teste exige rodar o Spark inteiro, em série. Com o desacoplamento, os pods geram código e plano em paralelo, em milissegundos — e o gate de CI fica rápido o suficiente pra rodar em cada Pull Request.
O problema · acoplamento

Hoje o plano nasce
de rodar o código.

fluxo atual — fila sequencial: para ter o History, rode o Job
Por que isso atrapalha (só para os testes)
Para gerar um caso de teste preciso subir o Spark e rodar o job inteiro. É lento (segundos a minutos por fixture), é serial (o gerador de plano espera o de código), e trava o paralelismo entre pods. Num gate de CI que roda a cada PR, isso é caro demais. Atenção: em produção esse acoplamento é correto e fica — History vem mesmo de rodar jobs reais. O problema é só na geração de fixtures.
A proposta · contrato no meio

Os dois leem o
mesmo scenario.yaml.

proposta — nenhuma seta horizontal entre os geradores: eles são independentes

É o mesmo princípio da tomada: produtor e consumidor nunca se falam direto — concordam só no formato. Aqui o "formato" é o scenario.yaml. Como os dois leem o mesmo scenario_id, o bug no código e o bug no log correspondem por construção, sem um precisar rodar o outro.

O contrato concreto · caso skew_on_join_30x

O scenario.yaml real.

Não é teoria: este contrato já está provado com um job.py e um event log reais que rodamos no Spark 4.1.2. Os campos-chave:

scenario_id: skew_on_join_30x anti_pattern: class: data_skew_on_join_key # customer_id=7 = 80% das linhas severity: high code_generator: # -> produz job.py emits: job.py anti_pattern_line: 58 # a linha do join com o bug plan_generator: # -> produz o event log emits: event-log.ndjson strategy: synthesize # A (rápido) | run_real (B, fiel) expected_signals: join_operator: SortMergeJoin hot_partition: { stage: 4, single_task_shuffle_read_records: 200100 } oracle: # -> mantém o gerador de plano honesto cadence: weekly on_divergence: fail_and_open_issue acceptance: # -> vira o gate de CI root_cause_includes: [data skew, customer_id, SortMergeJoin]
O que isto garante
Um arquivo declara o bug, define o que cada gerador produz, diz o que o log tem que conter, e fixa o que o Apex precisa detectar. Tudo amarrado por um scenario_id. É a fonte única de verdade do caso de teste.
As duas estratégias · e o oráculo

Rápido no dia a dia.
Fiel quando precisa.

Estratégia A · synthesize
Sintetiza o log direto
O gerador de plano escreve o event log a partir do scenario.yaml, sem rodar Spark. Milissegundos por cenário. É o motor do dia a dia e o que roda no gate de CI a cada PR.
Estratégia B · run_real
Roda o Spark de verdade
Faz spark-submit do job.py e captura o event log real. Lento, mas é a verdade. Não roda toda hora — só periodicamente, como oráculo.
o oráculo: roda o real de vez em quando e confere se o sintético não desviou do Spark

O porém de desacoplar é a fidelidade — um log sintético pode não bater 100% com o Spark real. O oráculo resolve: se A e B divergem, o gerador sintético está errado sobre o Spark e abre uma issue. Desacoplado no dia a dia, vigiado periodicamente.

Como encaixa no Apex inteiro

Duas fontes,
o mesmo destino.

produção e teste alimentam o mesmo ClickStack; os Watchers leem dos dois pela mesma interface

O ganho de encaixe: os Watchers não sabem (nem ligam) se o event log veio de um job real em produção ou de um cenário sintético de teste — os dois entram pela mesma interface ApexEventSource e pousam no mesmo ClickStack. Isso é o que torna os fixtures fiéis ao que roda em produção, e o que faz o mesmo Watcher servir nos dois mundos.

O que o time precisa debater

Faz sentido?
Os pontos em aberto.

A proposta não é fechada — estes são os trade-offs que valem decisão coletiva antes de virar ADR:

Fidelidade
Quão fiel o log sintético precisa ser? Sintetizar dá velocidade, mas pode não capturar nuances do Spark real. O oráculo semanal é folga suficiente, ou casos críticos deveriam sempre usar run_real?
Estratégia padrão
A (synthesize) como default, ou começar por B (run_real)? Começar pelo real dá confiança mas é lento; começar pelo sintético é rápido mas exige construir o oráculo cedo. Qual primeiro na Sprint 1?
Ownership
Quem é dono de cada gerador? O de código e o de plano podem ser pods diferentes (é o ponto do desacoplamento). Como dividir, e quem cuida do scenario.yaml (o contrato)?
Cadência do oráculo
Semanal, ou a cada mudança no gerador de plano? Mais frequente = mais confiança, mais custo de Spark. Onde fica o equilíbrio?
Vocabulário
Alinhar os dois eixos de "Pod". O Pod 1/2/3 do diagrama é estágio de pipeline; os Watchers (skew, memória) são outro corte. Deixar explícito qual é qual pra não confundir o time.
